The model gateway: switching provider should be a configuration change

One layer between applications and models turns a strategic dependency into an operational routine.

AL Ops · Published 30 September 2026

Among the architectural decisions that reduce lock-in, the model gateway does a great deal for its size.

What it is

A model gateway is one standard interface between every application or agent and the models behind it. Applications request a capability; the gateway decides which approved model serves the request, calls it, and returns a consistent response. Applications hold no provider-specific code or keys.

Routing turns model choice into policy

  • Data classification: restricted data goes only to models in approved locations or on your infrastructure.
  • Task: routine classification goes to a small model; complex reasoning to a stronger one.
  • Latency and language: interactive channels use fast models; local-language work uses models tested for it.
  • Cost: budgets and limits shift traffic, with approval for exceptions.

What it makes possible

Onboarding a model becomes a configuration and evaluation task: register it, test it against your own cases, route a slice of traffic, and widen the route as evidence supports it. Retiring a model works in reverse, and fallbacks keep services running during a provider outage.

The gateway is also where calls are recorded, so cost, quality and compliance reporting come from one source.

What to ask a vendor to show

  • Commercial, open-weight, sovereign and in-house models behind the same interface.
  • Routing policies managed centrally, without application changes.
  • Traceability of routing decisions and invocations.
  • A representative workload moved between two providers by configuration alone.

A switch is still a new evaluation. Configuration makes the move cheap; evaluation makes it safe.
